## 🎯 The Challenge

> 📌 You are building on **your own fork** of the company's **[monorepo](https://github.com/4GeeksAcademy/ai-engineering-company-project-monorepo)** selected at the beginning of the course — not on a new repository.

You already know how to pick the right agent mode for each task. The problem now is not how you use your agent, but that the team has as many ways of working as it has agents. Your CTO has opened a ticket with a specific request: define the **common minimum** that any agent — and any person — must respect when working in the company monorepo. The rules must apply equally to someone who has just joined with no experience, to a junior profile and to a senior one: nobody works with an agent that has more permissions than everyone else's.

The entry point is an `AGENTS.md` file at the root of the repository, the open convention read by most coding agents. That file is **the single source of truth**: if your tool uses its own instructions file, that file only points to `AGENTS.md` and never duplicates rules. And because the agent loads it in every session, every line costs tokens in every conversation: `AGENTS.md` is an index of what is non-negotiable, and the detail lives in separate rules, one per concern.

This work is about **how work gets done**, not **what the company is**. `AGENTS.md` does not describe the business, the clients or the operation: that lives in the monorepo's `CONTEXT.md`. The company briefing only helps you find the risks that must become limits.

There are two common traps. The first is writing a rule about secrets without checking whether the repository actually protects them: **before accepting any environment rule, verify that the repository does what the rule promises and fix whatever is missing**. The second is accepting the rules just because they exist. A rule that doesn't change what the agent does is either unnecessary or badly written, so **you need a baseline: how the agent behaves before the rules exist**, so you can later prove that they do change something.

> **From:** your CTO
> **Subject:** Ticket — minimum rules for working with agents in the monorepo
>
> Everyone works with their agent however they like, and it shows in the Pull Requests. I don't want a fifty-page manual. I want the non-negotiable minimum, the same for someone who just joined and for someone who has been coding for years. Seniority changes how you review what the agent produces, not what the agent is allowed to do.
>
> At a minimum, the brief covers three areas. In each one I'm leaving you things I've already seen happen on this team; all of them must be covered by some rule, but they are not the complete list.
>
> 1. **Coding conventions and style.** Naming, formatting, linting and the idioms specific to this repository. If a tool can check a convention, the rule names the tool and the command. Anything that depends only on the agent's goodwill is not a convention, it's a wish.
>    - Package managers are **pnpm** for JavaScript/TypeScript and **uv** for Python, no exceptions. I've already seen an `npm install` and a `pip install` in this repository: the dependency works on one machine and isn't recorded anywhere.
>    - Lockfiles that don't get committed, or that someone edits by hand to resolve a conflict. The lockfile is versioned and regenerated by the tool, never by a person.
>    - A three-line change buried in a four-hundred-line diff, because the agent reformatted the whole file. Formatting goes in its own commit, or it doesn't go in.
> 2. **Anti-patterns and explicit taboos.** A negative list: libraries, patterns and shortcuts the agent is forbidden to use. Each prohibition with its reason in one line. A "no" without a reason is the first thing someone skips.
>    - Errors silenced so that something "works": an `except: pass`, an `any`, an `eslint-disable`, a commit with `--no-verify`.
>    - A failing test that was deleted or marked to be skipped. A red test gets fixed or discussed, not hidden.
>    - URLs, ports and identifiers hardcoded in the code, which work locally and break in any other environment.
> 3. **Environment and access.** Where secrets live and where they must never appear, how external APIs are integrated and, above all, at which moments the agent stops and asks for human approval before executing something destructive or high-risk.
>    - A `.env` pushed by mistake and "deleted" in the next commit. It's still in the history: a leaked key gets revoked and rotated; removing the file is not enough.
>    - An API key in frontend code. Everything that reaches the browser is public, including anything with a prefix like `NEXT_PUBLIC_`.
>    - A `git add .` that took files nobody reviewed, a `git clean -fdx` that deleted someone's local `.env`, and a `git push --force` on a shared branch.
>
> If you think something is missing from that minimum, propose it and justify it. But don't inflate it: every line of `AGENTS.md` is paid for by every session of every agent.
>
> Read the company briefing looking for what could go wrong, not for what to build. That's where the red lines are that a generic rule will never cover.
>
> The acceptance criteria are the ones in the checklist. I give sign-off on the Pull Request, and what matters most to me is not that the rules exist, but seeing that they change what the agent does.

### Complementary knowledge: what goes in `AGENTS.md` and what goes in a rule

**`AGENTS.md`** is always loaded. It contains the essentials: what the file is for, the stack and key commands (install, format, lint, tests), the red lines, and a rules index that says when each one applies.

**A rule** (`.agents/rules/<topic>.md`) covers a single concern and declares in its header its **scope** (which files it applies to), its **activation mode** (always, by file pattern or on demand) and its **reason**.

To make a rule verifiable, use normative verbs — **MUST**, **MUST NOT**, **SHOULD** — and avoid "try to", "where possible" or "if it makes sense". Human-approval triggers read best in event-driven EARS format: _"When the agent is about to delete a file or folder, the agent shall stop and request approval before executing it."_

> 🔀 **PR approved → merge into `main`.** Otherwise, the rules never reach the main branch and the next development starts with agents working without them.

## 🌱 How to Start the Project

1. Work on your fork of the company monorepo. Create the branch `feature/agent-rules`.
2. Read your company briefing with a risk mindset and note what sensitive data it handles, which countries and currencies it operates in, and which systems exist.
3. Before writing any rule, prepare and run your baseline tests. That result is your starting point.
4. Make a separate commit for each phase: baseline, `AGENTS.md`, rules, repository hygiene and verification. The history is part of the submission.

## 💻 What You Need to Do

### Baseline

- [ ] Design at least four test tasks (_probes_) meant to tempt the agent into breaking a rule, with at least one for each area of the ticket: conventions, taboos, and environment and access. For example: asking it to add a library to solve something trivial, to leave an API key in the code "just for testing", or to delete a folder that "isn't needed".
- [ ] Always use fictitious values in the probes. Never paste a real secret into a prompt.
- [ ] Run the probes that involve destructive or risky actions in Plan or Ask mode, so the agent describes what it would do without executing it.
- [ ] Run all the probes without rules and record in `docs/agent-rules/probes.md` what the agent did or proposed in each one.

### `AGENTS.md`

- [ ] Create `AGENTS.md` at the root of the monorepo as the single entry point for any agent.
- [ ] Include the purpose of the file, the repository's stack and key commands, the non-negotiable red lines, and a rules index stating when each one applies.
- [ ] Keep `AGENTS.md` under 120 lines. The detail lives in the rules, not here.
- [ ] Don't describe the company, its business or its operation. Link to `CONTEXT.md` for that.
- [ ] If your tool uses its own instructions file (`CLAUDE.md`, `.cursor/rules/`, `.github/copilot-instructions.md`…), make it only point to `AGENTS.md`, without duplicating content.

### Project rules

- [ ] Create the `.agents/rules/` directory with one rule per concern, each with a header for scope, activation mode and reason.
- [ ] Create the **coding conventions and style** rule: naming for each language in the stack, formatting, linting and the idioms specific to the monorepo (where each type of piece goes according to the folder structure).
- [ ] In that rule, set pnpm and uv as the only package managers, with the allowed commands to add, remove and install dependencies in each one.
- [ ] For each convention a tool can check, name the tool and the command, and add the minimum configuration that makes it possible (for example, `.editorconfig` or the language formatter's configuration).
- [ ] Create the **anti-patterns and taboos** rule: at least six explicit prohibitions, each with its reason in one line and the allowed alternative when there is one.
- [ ] Create the **environment and access** rule: where secrets live, where they must never appear (code, logs, commits, prompts, test data) and how an external API is integrated.
- [ ] Include in that rule at least five human-approval triggers in event-driven EARS format, covering at least: deleting files or folders, rewriting Git history, adding or removing dependencies, changes to environment or infrastructure files, and changes to `AGENTS.md` or to the rules themselves.
- [ ] Add at least one more rule you consider part of the minimum and justify it in the Pull Request. Some candidates: Git and commit workflow, definition of done (what the agent checks before considering something finished), scope discipline (don't touch anything outside the ticket), ambiguity protocol (ask and state assumptions instead of filling in gaps). You can also propose another one.
- [ ] Make sure every case your CTO mentions in the ticket is covered by at least one rule, written as a verifiable rule and not as a copy of the anecdote.
- [ ] Write all rules with normative verbs (MUST, MUST NOT, SHOULD) and without ambiguous wording.

### Company red lines

- [ ] Identify in the briefing at least two risks specific to your company — for example, the type of personal or sensitive data it handles, operating across several countries, currencies or languages, or legacy systems that can't be touched without coordination — and turn them into concrete rules or taboos.
- [ ] Next to each red line, state which part of the briefing it comes from.

⚠️ **IMPORTANT:** red lines must be derived from your assigned company's briefing. A generic set of rules that would work equally well for any company will not be accepted.

### Repository hygiene

- [ ] Check that the repository does what your secrets rule promises and fix whatever is missing.
- [ ] Create `.env.example` with the names of the required variables and fictitious values.

### Verification

- [ ] Run the same probes again, in the same mode, with the rules active, and record the result next to the baseline.
- [ ] For each probe where the behaviour didn't change, adjust the rule or justify why it doesn't apply.
- [ ] Open a new agent session, ask it to explain the project rules without help, and check that it identifies the red lines and the approval triggers.
- [ ] Review everything the agent has written before committing it. You are responsible for every line that enters the repository.

## ✅ What We Will Evaluate

- [ ] `AGENTS.md` exists at the root, has fewer than 120 lines, and includes stack, key commands, red lines and rules index.
- [ ] `AGENTS.md` contains no business description and links to `CONTEXT.md`.
- [ ] Tool-specific instructions files, if they exist, only reference `AGENTS.md` and don't duplicate rules.
- [ ] `.agents/rules/` contains at least four rules: the three areas of the ticket plus one justified additional rule.
- [ ] Each rule declares scope, activation mode and reason.
- [ ] The conventions rule sets pnpm and uv as the only package managers and states their commands.
- [ ] Each tool-checkable convention names the tool and the command, and the corresponding configuration exists in the repository.
- [ ] The taboos rule has at least six prohibitions, each with its reason.
- [ ] There are at least five human-approval triggers in EARS format covering the five minimum cases.
- [ ] Each of the nine cases in the CTO's ticket is covered by at least one identifiable rule.
- [ ] No rule uses ambiguous wording such as "try to", "where possible" or "if it makes sense".
- [ ] There are at least two red lines specific to the assigned company, each traceable to a part of the briefing.
- [ ] The repository excludes environment files from version control, `.env.example` exists with fictitious values, and there are no secrets in the history.
- [ ] `docs/agent-rules/probes.md` contains at least four probes, covers the three areas of the ticket, and compares baseline and with-rules results.
- [ ] At least three probes show a behaviour change attributable to a specific rule.
- [ ] The commit history separates the phases of the work; there is no single commit grouping everything.

## 📦 How to Submit

Push your `feature/agent-rules` branch to your fork of the monorepo and open a Pull Request against the main branch.

In the Pull Request description include:

- Your company's red lines and which part of the briefing each one comes from.
- The additional rule you added to the minimum and why.
- A summary table of the probes: what the agent did without rules, what it did with rules, and which rule caused the change.
- A rule you discarded to avoid inflating the minimum, and why.
